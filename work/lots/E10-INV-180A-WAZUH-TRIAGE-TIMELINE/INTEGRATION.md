# E10-INV-180A — Authorized Wazuh Search Job result chronology

**Material integration:** the completed first-party Event Search Job from PR #55 is now a useful, chronologically ordered Wazuh triage view, not only opaque hash IDs. On the same authenticated loopback analyst screen, each matched event shows exact normalized UTC source time, Wazuh rule and agent IDs, optional 0..16 rule level and operator-assigned feed ordinal; clicking the row still goes through the existing independent Case/source authorization path. This is **not a new detection/correlation engine** and does not treat timestamps or rule level as a causal finding.

## Implementation and trust

- Reuse the existing Go Event Search Orchestrator, Case+Timeline owner pagination, and typed-source re-open for **every match** from PR #54/#55. No extra owner traversal, no new query evaluator, no SaaS, no paid API.
- The existing Wazuh backend, immediately **after** typed-source authorization of a matching entry, retains only stable Entry ID + normalized UTC timestamp + exact Wazuh rule/agent IDs + optional rule level + provenance feed ordinal. Metadata comes from the SAME source bytes validated at import, not a second file read or client-supplied data. The source's timestamp comes from the authorized Timeline, not Wazuh metadata alone.
- After `Event Search.Execute` actually completes, the server verifies that every SearchJob ResultRef has exactly one metadata row (and no other rows). It sorts hits chronologically using actual RFC3339Nano time instants, breaking ties with Entry ID. Any denial/incomplete owner, source identity change, mismatch, duplicate or cancellation fails the **entire** receipt. The HTTP receipt keeps the existing format and adds `search_hits` as a compatible optional data element. No raw payload, arbitrary message, hostname, IP, security token or unrelated-Case metadata is disclosed.
- The browser rechecks that `search_hits` is a one-to-one bijection with the Job's 0..200 authorized refs, contains valid source metadata shapes, then renders **textContent only**, with source buttons that use the existing owner route on every click. Malformed/partial receipts produce no list and **no replay export**. Older synthetic test receipts with no metadata remain displayable as opaque references, preserving existing UI compatibility.
- A previously supported explicit JSON replay/export remains **criteria-only**: no timestamps, source metadata or event refs from this triage view are added to its file. Its manual re-execution still reauthorizes current Case/Timeline/typed sources.

## Acceptance / limits

- GitHub Actions exact-head `investigation-timeline-runtime` on Linux/macOS/Windows (Go tests, first-party browser tests), `engineering-kernel` unchanged mandatory coverage policy, no merge while any required CI/L2 fails.
- End-to-end test imports two operator Wazuh feeds sharing the same original alert ID and confirms two distinct selected authorized entries, exact UTC ordering, agent/rule, known rule levels 12 and 6, feed provenance 1 and 2, absence of out-of-range event, no raw descriptions/bearer/foreign tenant, and existing source-open drilldown. Browser tests verify UI chronology and fail-closed unknown Entry ID, unknown level, injected rule, mismatched rows, no partial export.
- Local **synthetic** operator IAM, not production permission enforcement; no live Wazuh feed, durable index, server Saved Search, canonical Case mutation, signed chain of custody or production correlation SLO. Context source time can be wrong in the original event; chronology is descriptive, not corroborated.
