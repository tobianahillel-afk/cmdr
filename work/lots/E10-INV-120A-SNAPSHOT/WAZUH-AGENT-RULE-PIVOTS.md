# E10-INV-120A — authorized Wazuh agent/rule pivots

## Functional increment

An operator selects **offline Wazuh 4.x alerts.json JSONL** and an existing local Case. The existing code imports and normalizes the alerts, attaches them to the authorized Case, traverses Case/Timeline/typed-source access over actual loopback HTTP pagination, and produces a machine-readable investigation triage receipt. This increment makes that receipt actionable for host-level investigation by adding:
- `distinct_agent_ids` and `unknown_agent_ids` across the *authorized imported alerts*;
- `top_agents` (up to ten, ranked count descending, ties by agent ID ascending), containing only Wazuh `agent.id`, visible alert count, distinct known `rule.id` count, and highest **known source-reported** `rule.level` (nullable).

The existing per-rule frequency cohorts, five-minute time windows and Case summary are unchanged. These are retrospective alert statistics, **not** maliciousness scores, causal relationships, host attribution beyond Wazuh's identifier, or detections generated by CMDR.

## Reuse-first technology decision

Wazuh 4.x alert JSON has `agent.id` (e.g. `"001"`) and `rule.id` as strings. Reuse the existing per-alert identity map, Go `encoding/json`, the deterministic sorted aggregator, imported Timeline Entry IDs and the owner-authorized `collectDemoCaseTriageWithObserver`. An Elasticsearch/OpenSearch connector, third-party parser, database, stateful query engine or generic grouping framework is unnecessary for this bounded local 8 MiB / at-most-5,000-entry journey. No dependencies added. Relevant public Wazuh reference: https://documentation.wazuh.com/current/user-manual/ruleset/ruleset-xml-syntax/rules.html

## Security and verification

The extra agent metadata is read from **the identical input bytes** already normalized for import, not a second disk read. Correlation is carried out exclusively within the callback AFTER Case, Timeline Entry and typed-source read checks. Do not expose `agent.name`, agent IP, hostname, raw `full_log`, alert ID or source preview in the aggregate. Agent IDs are Wazuh source metadata, not permission evidence; only ASCII-decimal strings of at most 16 bytes are accepted, including leading-zero identifiers. Missing ID counts as unknown, not agent 000. Invalid explicit ID fails before writing any result. Unknown severity does not become zero; a true `rule.level=0` remains known.

Tests exercise a real CLI/disk owner snapshot + five imported alerts, mixed agent/rule values, distinct rule counting, denied principal's empty output, malformed agent metadata, and top-ten stable ties with level 0. Validation must be independently confirmed by exact-SHA GitHub CI. The local snapshot is operator-controlled and IAM is synthetic; this is **not** an authenticated production Wazuh collector, full forensic chain of custody, automatic rule correlation against live endpoints or a durable investigation backend. `OPEN-013` remains unresolved. Bounded functional scope, no new cross-tenant permission model.
